How can we connect any LLM / coding agent / harness to data.monster and let it operate the app · ingest data, author content, run analysis?

Ship an MCP server inside data.monster’s Rust backend, served as Streamable HTTP on 127.0.0.1 from the already-running app, built on the official Tier-1 Rust SDK (rmcp). MCP is the settled standard — every major harness (Claude Code, Cursor, VS Code, Codex, opencode, JetBrains, Gemini CLI) supports it as a client, and the “agent connects to a running desktop app over loopback HTTP” pattern has production precedent (Figma Dev Mode MCP Server). data.monster is unusually well positioned: the Rust backend already owns every operation an agent needs as per-domain command modules — the MCP tool layer is a thin wrapper over code that exists. The real design work is the tool catalog and the layered safety model: read-only by default, opt-in write, elicitation confirmations for destructive ops, audit log, transactions, and checkpoints.

1 · The standard is MCP · served as Streamable HTTP on loopback, not stdio

MCP has consolidated as the agent→app protocol (spec chain 2024-11-05 → 2025-03-26 → 2025-06-18 → 2025-11-25 → 2026-07-28 current, all changelog-verified; ~500M SDK downloads/month; official registry frozen at v0.1; TS/Python/C#/Go/Rust SDKs are Tier 1). For a desktop app that is already running, the transport is forced: stdio requires the agent to spawn the server and cannot attach to a running app; a separate process is blocked by DuckDB’s single read-write file lock; only in-process Streamable HTTP on 127.0.0.1 lets the Rust process that owns the DuckDB connection be the server. That is exactly Figma’s embedded Dev Mode MCP server pattern (127.0.0.1:3845). rmcp’s Streamable-HTTP server is a Tower service that nests into any axum router.

  • Spec 2026-07-28 made the protocol stateless, replaced server-initiated requests with MRTR, moved tasks to an extension; rmcp targets both 2025-11-25 and 2026-07-28 high
  • Every harness the team uses (Claude Code, Cursor, VS Code, Codex, opencode) consumes stdio + HTTP MCP servers today high
  • stdio remains viable later as a thin shim proxying to the running app (Obsidian Local-REST-API pattern) high
  • Community tauri-plugin-mcp-bridge (~50k dl/mo) exists but is community-maintained with frequent breaking releases · rolling our own axum mount is small medium

2 · The architecture, concretely

  • Start axum + rmcp Streamable-HTTP service at /mcp, bound to 127.0.0.1 only, from the Tauri setup hook
  • Auth: loopback binding (OAuth 2.1 §1.5 carve-out) + startup-generated bearer token; port+token written to a well-known file (~/.data-monster/mcp.json) that harness configs reference · no port drift
  • Tools are thin wrappers over existing Rust command modules · queries, files, tables, saved_queries, PageDoc storage, postgres · the same functions the Tauri invoke commands call; no second implementation
  • UI refresh: mutating tools emit Tauri events so the human sees agent actions live; get_app_status/notify cover long jobs
  • Everything stays in the one signed main exe · no sidecar binary to code-sign medium
  • Result: one server, one-liner config for any harness: {"mcpServers":{"data-monster":{"url":"http://127.0.0.1:<port>/mcp","headers":{"Authorization":"Bearer …"}}}}

3 · Tool catalog · split read/write, expose business content

Surveyed: Postgres/SQLite reference servers, MotherDuck (DuckDB), Supabase, Databricks, dbt, Hex, Deepnote, Evidence. Recommended surface:

  • Discovery (read-only, always on): list_tables, describe_table, list_saved_queries, list_pages/get_page (PageDoc JSON), search_workspace
  • Query: read_query (SELECT/SHOW/DESCRIBE enforced in Rust) vs write_query (CTAS/DDL) · split, not one SQL tool: split lets harness permission rules gate writes at the protocol layer; preview results carry rows_returned/total_rows/truncated (Hex pattern); export-to-CSV for big results (Deepnote pattern); MotherDuck caps (1024 rows / 50k chars) as default
  • Ingestion (write-gated): ingest (path/URL CSV/Parquet/JSON), import_postgres, list_ingestions
  • Content (write-gated): save_query, create_page/update_page (PageDoc spec is already agent-authorable JSON), set_table_tags · precedent is Hex/Deepnote (notebook-app servers), not the pure DB servers
  • App-control: refresh_ui, notify, get_app_status

4 · Safety model · layered, because no single layer holds

  • Read-only default; write opt-in (MotherDuck --read-write / postgres-mcp restricted-mode pattern), toggled in Settings + per-session scope
  • Annotate every tool (readOnlyHint, destructiveHint, idempotentHint) · defaults are pessimistic; spec marks hints untrusted: necessary, not sufficient high
  • Elicitation (stable spec, form mode; Claude Code + Cursor support it) = native in-band confirmation for destructive SQL and write-scope grants. Do not build on sampling · deprecated 2026-07-28
  • Transactions & checkpoints: agent write batches in BEGIN … ROLLBACK-able transactions (DuckDB is fully ACID); EXPORT DATABASE checkpoint before write sessions
  • Audit: append-only log (agent, tool, args hash, row counts) in a separate DuckDB file
  • Secrets stay in the app: Rust backend holds keys/tokens, never the agent; server-side scoping alone can leak (a Postgres-MCP-Pro restricted-mode bypass was reported Sept 2026) · defense in depth
  • Design for the harness grammar (ask/allow/deny per tool + input patterns · Claude Code modes, opencode permission rules): split tools make those rules expressible

5 · What is NOT the path

  • OpenAI Apps SDK / ChatGPT plugins: MCP-based but cloud-first · public HTTPS endpoint + review; nothing local-native remains high
  • Google A2A: agent-to-agent delegation, explicitly “not a replacement for MCP” · orthogonal (only if data.monster later is a delegable agent) high
  • Claude Desktop Extensions (.mcpb): distribution packaging for MCP servers, not a protocol · relevant later for one-click install high
  • Copilot extensions: GitHub/repo-centric; a local app reaches Copilot only as an MCP server anyway high
  • UI automation: CDP/Playwright on WebView2 (already proven in this repo) is a great e2e-test channel but a bad agent API · no typed semantics, no transactions. Computer use is last-resort (CUA 38.1% vs human 72.4% OSWorld; slow, token-heavy) high

Tensions

Tension

Protocol era split: the 2026-07-28 stateless redesign is large; clients and third-party docs are mixed between 2025-11-25 and 2026-07-28 behavior (Cursor docs still list SSE). Assessment: rely on rmcp’s era handling and test against real clients, not docs.

Tension

rmcp version confusion: crates.io README example shows 0.16.0 while the 2026-08-21 Tier-1 promotion cites stable 3.0.1. Assessment: pin what resolves today; read the 3.x migration notes first.

Tension

One SQL tool (Supabase/MotherDuck/Databricks) vs split read/write (SQLite reference): vendors rely on server-side read-only users; split buys protocol-level gating in harness permission rules. Assessment: split · cheap and composes with harness UX.

Tension

Safety layers each leak: spec calls annotations untrusted; a restricted-mode bypass in Postgres MCP Pro was reported (Sept 2026). Assessment: never one layer · read-only default + split tools + elicitation + transactions + audit together.

Open questions

  • Live per-client matrix: which connected clients negotiate 2026-07-28 vs 2025-11-25, and which actually surface elicitation forms (test Claude Code, Cursor, opencode, pi directly)
  • DuckDB time-travel-style undo (DuckLake / snapshots) as a cheaper agent-undo than EXPORT checkpoints
  • Whether to later ship a stdio shim exe + .mcpb bundle for one-click harness install (Windows signing cost)
  • pi extension angle: a thin extension/skill wrapping the same MCP surface · redundant if pi’s MCP client reaches localhost HTTP (observed in-session, not web-verified)
  • ARD (Agentic Resource Discovery) as an alternative to a hand-maintained tool catalog
